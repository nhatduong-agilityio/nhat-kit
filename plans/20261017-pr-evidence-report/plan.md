# PR report artifact for every PR

Status: done · Source: request (follow-up to P-22, `plans/20261016-evidence-artifact/plan.md`)

## Goal

Every PR opened through `/devkit:ship`, `/devkit:task`, or `/devkit:git pr` gets one published "PR report" artifact — Summary, AC → evidence table with ✅/⚠️/❌ status, verification output, Screenshots/GIF (or `None (no UI change)` when the change isn't UI-visible), manual test steps, risks, and the commit SHA, with a one-line "X/Y ACs met" summary and `<details>`-collapsed long output for scanability — not just UI-visible changes as today. The PR body itself slims to Summary → Closes/Refs → a link to that artifact (covering the AC table, verification output, Screenshots/GIF, and manual test steps) → Risks and impact (kept inline, not moved to the artifact) → Checklist, with `Closes #N` always kept literally in the body. With no Artifact tool available, the PR falls back to today's full inline body, unchanged.

## Approach

Keep the existing "main-session-only" constraint and build on it rather than reopening it: the orchestrating skill (`ship`, `task`, or `git`'s `pr` mode) always builds the report content and publishes it as one artifact before delegating to `git-manager`; `git-manager` never touches the Artifact tool, it only ever receives a finished link (slim-body case) or the finished full content (fallback case). The PR body slims to `## Summary` / `Closes #`+`Refs:` / `## Full report` (the link, covering the AC table, verification output, Screenshots/GIF, and manual test steps) / `## Risks and impact` (its own inline section, not moved to the artifact — the user's "slim down" instruction named What, Why, How-tests, and Screenshots as the things to move out, never Risks, so it stays put) / `## Checklist`, in both template files. `Closes #N` stays a hard, literal requirement in the PR body in both branches, since GitHub only parses its auto-close keywords from the PR description itself. Because `git-manager` has no Artifact tool and so cannot open the artifact link to judge which checklist boxes have evidence, the orchestrating skill also passes it a short condensed checklist summary (one line per checklist item) and the Risks-and-impact text alongside the link — never the bare link alone — and, if it is ever handed both an artifact link and the fallback's full content in the same call, the artifact link wins for body shape and the full content is ignored.

Rejected alternatives:
- **Keep the body as-is and just add the artifact link alongside the full inline content** — rejected by the user's explicit decision 2 (slim down, don't duplicate).
- **Build the artifact inside `git-manager` itself** — rejected: `git-manager` has no Artifact tool (`tools: Bash, Read, Grep, Glob`, confirmed at `plugins/devkit/agents/git-manager.md:4`) and runs on the `haiku` model tier, not meant for composing a rich report page; the main-session-only constraint from P-22 doesn't change.
- **Gate the report artifact on "non-trivial" PRs instead of every PR** — rejected; the user explicitly confirmed every PR gets one.
- **Move `Risks and impact` into the artifact by default, same as the other sections** — rejected: the user's own "slim down" instruction enumerated What, Why, How-tests, and Screenshots as the content to pull out of the body; it never named Risks, so the plan doesn't extend the cut beyond what was asked.
- **Pass `git-manager` only the artifact link, trusting it to infer checklist completion** — rejected: with no Artifact tool, `git-manager` cannot open the link, so it would have no basis to tick any box; a condensed checklist summary (and the Risks-and-impact text) must travel alongside the link instead.
- **Let `ship`, `task`, and `git` each re-enumerate the report's content list in their own prompt text** — rejected: three independent copies of the same list drift the moment one of them is edited without the others (the failure mode a red-team pass caught); each now points at `conventions.md`'s "PR report artifact" section by reference instead of repeating it, which makes that kind of drift structurally impossible rather than something to catch with a grep.
- **Add charts/graphs (coverage trend, etc.) to the artifact** — rejected; out of scope per the request — "a little visualization" means status badges/color and `<details>` collapsing, not a charting library.
- **File this as a new `UPSTREAM.md` proposal row** — rejected; this is a follow-up/generalization of P-22, not a new upstream-tracked idea.

## Risks

| Risk | Signal | Mitigation |
| --- | --- | --- |
| `Closes #N` accidentally ends up only in the artifact, not the literal PR body — GitHub never parses auto-close keywords from a linked page, so the issue silently never closes on merge | A merged PR whose linked issue stays open; a template or `git-manager.md` edit that moves `Closes #` under `## Full report` instead of keeping it as its own line | Hard rule stated explicitly in both `conventions.md` (Phase 1) and `git-manager.md` (Phase 2), not just implied by convention; Phase 3 keeps `Closes #` as its own template line in both files; Phase 2's verify greps for the rule in both prompt files, Phase 3's for the field in both templates |
| The Artifact-tool-availability fallback in `git-manager.md` is wrong or missing, or the precedence between a link and full content given together is undefined — a headless/no-artifact run either crashes, silently produces a broken "Full report: (missing link)" body, or picks the wrong shape when handed both | A PR body with an empty or literal placeholder link; a run that errors instead of falling back; a slim body built from stale full-content input or vice versa | Phase 2 writes an explicit guard into `git-manager.md` (given neither, stop and report) and an explicit precedence rule (given both, the link wins); Phase 3 verifies the fallback branch's section names match exactly what Phase 3 kept vs. folded in the templates, so there's a concrete prose shape to reconstruct |
| Verification output or the commit SHA published in the report artifact exposes a secret, token, internal path, or personal data — a bigger blast radius than the old screenshot-only scrubbing rule, since the report now publishes for every PR, not only UI ones | A pasted command's output contains an `.env` value, a stack trace with an internal hostname, or similar, visible in an externally-hosted artifact | Phase 1 extends the existing screenshot-scrubbing rule in `conventions.md` to cover verification output and the commit SHA too: redact or omit the offending line and say why, the same as the screenshot rule already requires |
| Seven interdependent files (conventions, 3 skills, 1 agent, 2 templates) describing one contract can drift — one file renames or reshapes something the others still assume | A grep for the new heading name, a fallback section name, or the checklist-summary handoff comes back empty in one file but present in the others | Phase 2's verify block checks the report's name and the checklist-summary handoff across all four prompt files plus conventions.md in one pass (folded in after P-22's own precedent of combining `ship`/`task`/`git-manager` into one phase, instead of a separate standalone consistency phase); Phase 3's verify closes the loop by checking `git-manager.md`'s fallback section names against what the templates actually kept or folded, once both exist to compare |
| Publishing an artifact on every PR (not just UI ones) adds an Artifact-tool call to every `ship`/`task`/`git pr` run | Slower runs, or hitting an Artifact-tool limit/quota in a heavy-PR-volume project | Out of scope to add an exception — the user explicitly confirmed every PR; the existing no-Artifact-tool fallback already covers unavailability, just not covered here is "available but rate-limited," which would show up as the same fallback case |
